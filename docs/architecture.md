# AUMS System Architecture & Design Specification

**Version**: V1.0.1
**Status**: Stable / Baseline Document

---

## 1. Overview

The **AI Powered Autonomous Management System (AUMS)** is designed as a enterprise-grade academic management system. It employs a modern multi-tier architecture separating the client presentation layer, API gateway & business logic server, database storage engine, caching layer, object storage system, and AI support modules.

## 3. Core Architecture Layers

### 3.1 Backend Service Layer (Go 1.26 + Gin)
The backend service strictly follows the **Repository → Service → Handler** layered architectural pattern:

1. **HTTP Handler Layer (`internal/<domain>/handler.go`)**:
   - Parses HTTP request payloads and query parameters using Gin context.
   - Executes struct validations using `go-playground/validator/v10`.
   - Returns standardized responses via `response.Success()`, `response.SuccessWithMeta()`, `response.Error()`, and `response.ValidationError()`.
2. **Domain Service Layer (`internal/<domain>/service.go`)**:
   - Encapsulates business logic, authorization enforcement, calculations (e.g., SGPA/CGPA formulas), and transaction orchestration.
3. **Repository Layer (`internal/db/generated`)**:
   - Executes database operations generated by `sqlc` from raw SQL queries (`database/queries/*.sql`).
   - Guarantees compile-time type safety and zero runtime ORM overhead using `pgx/v5`.

### 3.2 Frontend Architecture (Next.js 16 App Router)
The frontend enforces a **Feature-First Capsule** modular pattern:
- `app/`: Next.js App Router layout handlers, page entries, loading fallbacks, and error boundaries.
- `features/<domain>/`: Encapsulated domain components, custom hooks (`use-<domain>.ts`), Zod schemas, types, and services.
- `components/ui/` & `components/shared/`: Atomic UI primitives (buttons, dialogs, drawers, data tables) built using Tailwind CSS v4 and Radix UI primitives.
- `services/api/client.ts`: Axios client instance equipped with request interceptors for JWT header injection (`Authorization: Bearer <token>`) and response interceptors for token refresh queues.

## 4. Authentication & Authorization (RBAC)

### 4.1 Authentication Flow
1. **User Login (`POST /api/v1/auth/login`)**:
   - User submits email and password.
   - Backend verifies password hash using bcrypt.
   - Backend generates a signed JWT Access Token (short-lived, e.g., 15 mins) and Refresh Token (7 days).
2. **Authenticated Requests**:
   - Frontend includes the Access Token in the HTTP `Authorization` header (`Bearer <access_token>`).
   - Backend `pkg/middleware/jwt.go` validates token signature and claims.

### 4.2 Role-Based Access Control (RBAC) Matrix
AUMS maintains a dynamic permission table with 7 primary system roles:
- `SUPER_ADMIN`: Unlimited access across all institutions, roles, and settings.
- `INSTITUTION_ADMIN`: Controls campus setup, academic years, schools, and departments.
- `DEAN`: Oversees faculty allocations, curriculum definitions, and academic approvals.
- `HOD`: Manages department course offerings, timetables, and class sessions.
- `FACULTY`: Marks attendance, submits internal assessment marks, and enters exam grades.
- `STUDENT`: Registers for course offerings, views timetable schedules, exam results, and transcripts.
- `PARENT`: Views dependent student attendance metrics and published semester scorecards.

## 5. Storage & External Services

- **Database**: PostgreSQL 17 serves as the primary relational store.
- **Cache**: Redis 8 stores transient session tokens and permissions.
- **Object Storage**: MinIO (S3-compatible) provides object storage for file uploads (avatars, syllabus files, assignments).

---

## 6. AI Architecture (Future/RAG Scope)

AUMS includes structural hooks for AI extensions:
- **Retrieval-Augmented Generation (RAG)**: AI query interface to allow students and faculty to search university policies, course catalogs, and academic regulations.
- **Automated Timetable Generation**: AI constraints engine to resolve room allocation and faculty availability conflicts.
